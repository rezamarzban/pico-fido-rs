# ATECC608A secure element

The chip does six things and nothing else. Everything else runs on the Pico.

| In the chip | Chip command | Where in the firmware |
|---|---|---|
| Credential private keys (7 slots, never readable) | - | slots 0-6 |
| Attestation private key (1 slot, created once) | - | slot 7 |
| Key generation | GenKey (create) | `se/ecdsa.rs` `random()` |
| ECDSA P-256 signing | Nonce (pass-through) + Sign (external) | `sign()` |
| Public key extraction | GenKey (public mode) | `import()` |
| Random numbers | Random | `env/rng.rs` (seed of a ChaCha20 DRBG) |

Two chip counters support this, without extra commands in the list above: **Counter 0** is the
signature budget (the chip stops signing at its limit, see below) and **Counter 1** is the
round-robin cursor that picks the slot for the next credential (it must survive power cycles, and
the chip counter is the cheapest place for it).

On the Pico: OpenSK with its standard key-value store, ClientPIN (PIN hash in flash),
SHA-256 / HMAC / AES / HKDF / ECDH in software, BOOTSEL as user presence, USB.

## Wiring
Part: ATECC608A-**SSHDA**-B = 8-lead SOIC, I2C (datasheet DS40001977B, pins seen from the top).
| ATECC608A SOIC-8 pin | Signal | Pico / RP2040-Zero |
|---|---|---|
| 5 | SDA | GP14 (I2C1 SDA) |
| 6 | SCL | GP15 (I2C1 SCL) |
| 8 | VCC | 3V3 |
| 4 | GND | GND |
| 1, 2, 3, 7 | NC | not connected |

I2C address 0x60 (config byte 0xC0), 100 kHz. Internal pull-ups are enabled; most breakouts have
their own. The SSD1306 display stays on I2C0 (GP16/GP17), so the two never share a bus. Without the
chip the firmware halts at start-up (the credential keys and the RNG seed come from it).

## Slot layout (generated by `tools/gen_atecc_config.py`)
* Slots 0-6: ECC P-256 private key, secret, **LimitedUse**, external signatures only, no ECDH, no
  PrivWrite, **GenKey allowed** (so keys can be regenerated after the zones are locked), public key
  derivable. Config `A1 20` / `13 00`.
* Slot 7: the same, but **not** LimitedUse, so attestation does not spend the signature budget.
* Slots 8-15: unused (general data slots, no ECC).

A credential ID holds a 32-byte *handle* `[01][slot][6-byte public-key fingerprint][zeros]` inside
OpenSK's normal encrypted credential ID. `import()` rejects a handle whose slot was recycled.
Registrations beyond 7 **evict the oldest credential**: the key is overwritten in the chip and that
credential stops working.

## Provisioning
```
python3 tools/gen_atecc_config.py --slots 7 --budget 500 -o out    # or --base your_read_config.bin
atecc ... write-config out/atecc608a_fido_config.bin
atecc ... counter-init 0 -500        # AFTER write-config (it resets counters). 500 signatures left.
atecc ... counter-read 0 -r          # must show 500
atecc ... lock-config                # irreversible
atecc ... lock-data                  # irreversible; GenKey stays enabled on the key slots
python3 tools/make_attest_cert.py --out attest      # once: attestation key + self-signed certificate
```
`out/atecc608a_fido_config.bin` is a ready 7+1-slot image (the budget text inside is only
documentation: the budget is whatever you set with `counter-init`). Check any dumped chip with
`gen_atecc_config.py --check cfg.bin`.

### Attestation key and certificate
`tools/make_attest_cert.py` (needs the `cryptoauthlib` and `cryptography` Python packages, the chip on
a host I2C bus) does GenKey in slot 7, has the chip sign a self-signed X.509 certificate for that
public key, and writes:
* `attest_cert.der` / `.pem`: the certificate,
* `attest_key.hex` / `.pem`: the 32-byte **handle** of the key (not a secret; it only names the slot
  and carries a fingerprint of the key that must be in it).

The token then needs the certificate and the handle once, through OpenSK's attestation material
(`config_command` feature: `tools/configure.py --certificate=attest/attest_cert.pem
--private-key=attest/attest_key.pem`). It refuses to overwrite an existing key unless you pass
`--regen`. `python3 tools/make_attest_cert.py --selftest` checks the tool without hardware.

What attestation is used for: U2F registration always; FIDO2 registration only if
`use_batch_attestation` is set to `true` in `src/env/mod.rs` (default `false`: packed
self-attestation with the credential key). Note the privacy cost of turning it on: the certificate is
unique to this device, so every site can recognise it.

## Signature budget
Counter 0 starts at 2097151 - N. Each use of a LimitedUse key increments it first; at 2097151 the
chip refuses. The counter is **shared by all credential slots** (a device-wide total) and cannot be
reset or raised once the config zone is locked. When it reaches zero the firmware refuses user
presence (LED/timeout) and any signature that still reaches the chip is rejected by the chip.

## Acceptance test on real hardware (do this before locking a chip you care about)
1. `counter-read 0` equals the budget you set; sign 3 times through a browser/`fido2` tool; it drops by 3
   (if GenKey/public-key calls also consume budget you will see it here: adjust N).
2. Set a tiny budget on a spare chip (e.g. 3), confirm the 4th signature is refused.
3. Register 8 credentials: the first one must stop working, the rest must still work.
4. Unplug/replug: the slot cursor (Counter 1) and budget must persist.
5. After the attestation step: a U2F registration succeeds (e.g. webauthn.io with a U2F-only
   option), and does not change Counter 0.

## What this design does not protect
* There is no PIN or authentication in the chip. Whoever can talk to the chip on the I2C bus (code
  running on the Pico, or a probe on GP14/GP15) can ask it to sign, until the budget is used up. The
  PIN (ClientPIN) is checked by the Pico firmware only.
* The I2C bus is not encrypted.
